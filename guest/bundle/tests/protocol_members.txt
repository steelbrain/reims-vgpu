# The register of the Metal protocol members the bundle's classes answer, and how each is
# answered: tests/protocol_members_tests.mm walks every member of every MTL* protocol a class of
# ours adopts, through the Objective-C runtime, and fails on a member this file does not list, a
# line no class has, or a kind the code contradicts. Its header says what each kind means and
# what is checked of it. A new member (a new macOS, a new class or protocol) fails the test until
# it is listed here; the test's --propose prints a line for each, with the kind the code suggests.
#
# One line per member, "selector kind text", under the [Class] that answers it: a member a
# subclass inherits from a class of ours is listed under that class, and one only a base that is
# not ours answers, or no class answers, under the class that adopts the protocol. The protocols
# are those of the Mac the test runs on (its Metal.framework), which the guest's macOS may differ
# from by a few members.
#
# The reasons several lines share:

%debug debug groups, signposts and markers name work for Metal's capture and profiling tools; no result, order or value the guest sees changes, and the device has no such tools
%no-peers a view of the object on another GPU of a peer group: no buffer or texture of the device is one, and Metal answers nil for an object that is not (measured for a texture: M3 Max)
%no-sparse the device makes no sparse buffers or textures (their creators are RGFX_UNSUPPORTED), so no resource of it has a sparse tier, tiles or a mip tail
%pipeline-reflection Metal answers nil for a pipeline a device makes, reflection asked for or not (measured: M3 Max, compute and render; AMD 5300M and Intel 630, render)
%no-validation the device validates no shader, and Metal answers MTLShaderValidationDisabled for a pipeline made without validation (measured: M3 Max, compute and render; AMD 5300M and Intel 630, render)
%absent-as-metal none of Metal's own devices answers it either (measured with respondsToSelector:, M3 Max on macOS 27 and the AMD 5300M and Intel 630 on macOS 26.7.1), so a caller that sends it to any device checks first
%base-creator left to the base, as tests/inherited_tests.mm lists, with why
%base-spi an MTLDeviceSPI query, setter or tool hook the IOGPU base answers from its own state; the device answers every member of MTLDevice itself. tools/base_answers_probe.m compares what the base answers on this device with Metal's own devices (aud-tests-04)
%spi-unverified an MTLDeviceSPI feature query the M3 Max, the AMD 5300M and the Intel UHD 630 all answer YES (measured, tools/base_answers_probe.m), and the IOGPU base answers NO here: what it gates, and whether the lane carries that, is not established, so the base's NO stands until it is (aud-tests-04)
%spi-no-ray-tracing the IOGPU base answers NO, the lane's answer: it makes no acceleration structures (ray tracing is RGFX_UNSUPPORTED, and supportsRaytracing answers the host's NO), where Metal's devices answer YES
%icb-render-states the macOS 26 render states of an indirect command: the AMD 5300M and the Intel 630 raise an unrecognized selector for each, answering respondsToSelector: YES (measured, tools/oracle/oracle_icb.m), and so does the command (the M3 Max raises an API-not-supported exception)
%spi-no-counters the IOGPU base answers NO, the lane's answer: it samples no counters (counter sampling is RGFX_UNSUPPORTED, and counterSets is nil), where Metal's devices answer YES
%spi-no-dylibs the IOGPU base answers NO, the lane's answer: it makes no dynamic libraries (RGFX_UNSUPPORTED, and supportsDynamicLibraries answers NO), where Metal's devices answer YES
%spi-no-pipeline-libraries the IOGPU base answers NO, the lane's answer: it makes no pipeline libraries (newPipelineLibraryWithFilePath:error: is RGFX_UNSUPPORTED), where Metal's devices answer YES
%spi-no-shared-textures the IOGPU base answers NO, the lane's answer: it makes no shared textures or handles (RGFX_UNSUPPORTED), where Metal's devices answer YES
